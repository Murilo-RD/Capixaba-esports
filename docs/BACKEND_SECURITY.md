# Segurança e modelo de dados Moonastery

O navegador utiliza chave publishable/anon e Supabase Auth nativo com sessão persistida e refresh. O servidor exige `SUPABASE_URL` (ou VITE_SUPABASE_URL existente) e `SUPABASE_SERVICE_ROLE_KEY` ou `SUPABASE_SECRET_KEY`. Nunca utilizar VITE para a chave de servidor. Chaves publishable e JWT anon são recusadas como credenciais administrativas. `PUBLIC_APP_URL` (ou o alias legado `APP_URL`) é a origem configurada para convites/callbacks; configure Site URL, Redirect URLs, confirmação de e-mail e SMTP no Supabase. `BALLCHASING_API_TOKEN` é somente servidor.

Toda requisição interna valida bearer pelo auth.getUser no provedor e consulta membership atual; pending não acessa dashboard. Role/status não usam JWT metadata nem listas de e-mail. Mutação é whitelist Zod strict: APIs não aceitam notas manuais, role em profile.update, approved_by fornecido pelo cliente, author_id ou timestamps editoriais. Users.update e remoção passam por RPC serializada que bloqueia autoalteração e perda do último owner. Remoção primeiro suspende acesso no banco; se Auth delete falhar, conta permanece suspensa. Requisições seguintes falham independentemente do JWT ainda válido.

Tabelas privadas e públicas têm RLS; anon/authenticated possuem somente grants de leitura, com colunas privadas revogadas de anon e políticas por papel/usuário. Mutações são exclusivamente service_role no servidor; RPCs de escrita não têm EXECUTE para anon/authenticated/PUBLIC. Funções auxiliares de RLS ficam no schema não exposto moon_private, search_path vazio e executam consultas com auth.uid. public_player é uma consulta booleana pública deliberada sem dados privados. Funções RPC de escrita são invoker e conferem ator no banco; a chave de servidor é a fronteira administrativa. Configurações, pesos, informes, opiniões e métricas seguem entidades separadas.

Privacidade: publicHome e publicNews projetam colunas públicas explicitamente; não retornam emails, author_id, platform_id, feedback ou logs de processamento. Coaches/owners recebem identidades de jogadores para correspondência exata Steam/Epic; outras funções recebem projeção pública. Jogadores recebem somente seus reports, denúncias e instruções coletivas ou destinadas a eles. Histórico de processamento guarda snapshots imutáveis (grants service_role SELECT/INSERT); histórico de cartas gera uma nova linha por aprovação e alteração de arquétipo.

Uploads: imagens 5MB, tipos png/jpeg/webp com assinatura binária verificada; extensão é gerada pelo servidor e path prefixado com UUID do usuário. Base64 só existe no transporte, nunca na tabela. Foto de perfil aceita somente o Storage path do próprio usuário. Replays 20MB, .replay, SHA256 único e IDs de provedor/partida únicos para evitar binário alterado duplicado. Storage replays privado sem leitura pública e sem escrita client; uploads via servidor. Configure também limite HTTP request no hosting, pois multipart parsing e corpos sem Content-Length dependem dos limites do runtime.

Aprovação trava job e jogadores ordenados numa transação; consolida amostras aprovadas da noite com ponderação pela coverage de cada atributo, suavização configurável (0.2 default), teto configurável <=1, e âncora congelada da sessão anterior. A primeira carta válida estabelece a nota sem baseline artificial; novas aprovações da mesma primeira noite ficam ancoradas à primeira carta. A aprovação de noite anterior a uma já aprovada exige revisão explícita e é bloqueada para evitar rewind. Replays aprovados não podem ser reprocessados no fluxo comum. Ausência de todos atributos bloqueia aprovação; atributos parcialmente disponíveis permanecem null, overall exige todos com peso positivo. Alterar arquétipo recalcula composição atual e escreve histórico, sem mudar métricas originais. Pesos estatísticos/arquetípicos são propostas configuráveis; baselines SSL não são fabricadas.

Limitações operacionais: validação local não representa uma auditoria do projeto remoto, configuração Auth/SMTP ou Storage real. O processamento usa chamadas assíncronas ao provedor no servidor e a UI pode retomar pendências/429; não instala serviço externo de worker. Para alto volume, consumir os mesmos jobs por worker autorizado e configurar timeouts de hosting. Atualizações do serviço sem transação multi-entidade são auditadas após a alteração; RPCs sensíveis garantem atomicidade no banco.
